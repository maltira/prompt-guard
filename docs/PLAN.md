# План реализации

Реализация темы из [README.md](../README.md). Срок: 27.10 → 09.11.

## Решения

- **Область применения:** сканер входящей почты и документов для ИИ-ассистентов, модель угроз описана в README. Прямые запросы пользователя и джейлбрейки вне рамок.
- **Ответственность проекта:** вердикт детектора (атака или нет). Что делает с этим вердиктом ИИ-ассистент клиента - вне проекта, сквозной сценарий с реальным ассистентом не строится.
- **Язык:** Python 3.12 через `uv` (системный 3.14 слишком новый для части ML-библиотек).
- **LLM:** Claude Haiku 5.5 как судья. Настройки доступа и модель задаются в `.env`, а не в коде. Параметр `temperature` не передаётся (модель принимает только значение по умолчанию), воспроизводимость обеспечивает кэш ответов.
- **Данные:** датасеты и golden подготовлены без обращений к LLM.
- **Обучение LoRA и prompt tuning:** Google Colab / Kaggle (GPU T4). Инференс обученных адаптеров локально на CPU.
- **Сервисы:** FastAPI. Запуск через Docker Compose.
- **Эксперименты и графики:** pandas, scikit-learn, matplotlib.

## Что понадобится

| Что | Зачем |
|---|---|
| Доступ к Haiku 5.5 (токен и адрес в `.env`) | судья |
| Баланс на вызовы LLM | все прогоны с кэшем, сверить по тарифам Haiku 5.5 |
| Аккаунт Google Colab или Kaggle | LoRA и prompt tuning |
| Аккаунт Hugging Face | датасеты и базовые модели |
| Docker | запуск шлюза |

## Структура репозитория

```
data/             подробности в data/README.md
  schema.py       формат записи
  synth.py        шаблонные примеры для train и val
  build_golden.py, build_splits.py   сборка выборок
  custom/         ручные тексты golden (gold_*.py)
  raw/            исходные публичные наборы (не в git)
  splits/         train.jsonl, val.jsonl, golden.jsonl, stats.json
detectors/
  base.py         общий интерфейс Detector.predict(text) -> (label, score)
  llm_cache.py    клиент LLM с дисковым кэшем ответов
  implementations/   конкретные детекторы
    keyword.py      бейзлайн по ключевым словам
    embeddings.py   подход 1
    lora.py         подход 2 (инференс адаптера)
    prompt_tuning.py подход 3 (инференс)
    judge.py        подход 4 (Haiku 5.5)
    cascade.py      подход 5
notebooks/
  train_lora.ipynb
  train_prompt_tuning.ipynb
services/
  backend/        Dockerfile (контекст сборки: корень репозитория), gateway/ - FastAPI: /check, /compare, /detectors, /metrics, журнал
  frontend/       Dockerfile (nginx со статикой), public/ - страница демо
nginx/            входная точка: / во frontend, /api/ в backend (порт 8080), CORS не нужен
eval/
  run_eval.py     прогон детекторов по golden set
  plots.py        графики для статьи
results/<детектор>/  метрики и предсказания по выборкам; results/cache/ - кэш ответов LLM
docker-compose.yml
```

Ключевая идея: **все подходы реализуют один интерфейс `Detector`**. Тогда оценка, каскад и шлюз работают с любым из них без изменений.

## Этапы

### Этап 0. Подготовка (день 1) - выполнен

- `uv init`, зависимости, структура каталогов, `.env` с настройками доступа к LLM.
- Интерфейс `Detector` и формат записи данных: `{"id", "text", "label", "lang", "category", "source"}`.
- Кэш ответов LLM на диск (ключ: модель + промпт + параметры + текст), чтобы повторные прогоны были бесплатными и воспроизводимыми.

**Готово, когда:** проект ставится одной командой, тестовый вызов Haiku 5.5 проходит.

### Этап 1. Данные и golden set (дни 1–2) - выполнен

1. Найти 2–3 публичных набора по prompt injection на Hugging Face, проверить лицензию и качество разметки.
2. Написать собственные примеры в стиле демо (письма, документы), на русском и английском:
   - атаки разных категорий (подмена инструкций, выманивание секрета, притворные «системные сообщения»);
   - безопасные тексты;
   - **пограничные** безопасные тексты, похожие на атаку.
3. Удалить дубликаты и почти-дубликаты (по косинусной близости tf-idf), чтобы похожие тексты не попали одновременно в train и golden.
4. Разбить: train / val / golden. Golden: 450 примеров, поровну классов, написан и просмотрен вручную.
5. Зафиксировать golden (хэш файла в `data/splits/golden.sha256`) и больше не менять.

**Готово, когда:** три файла в `data/splits/`, статистика по классам, языкам и категориям. Результат и ограничения датасета: [data/README.md](../data/README.md).

### Этап 2. Оценочный стенд (день 3) - выполнен

- `eval/run_eval.py`: прогоняет любой `Detector` по golden, сохраняет предсказания, считает recall, precision, F1, долю ложных срабатываний, задержку (p50/p95), стоимость на 1000 запросов.
- Отдельные метрики по категориям и по пограничным примерам.
- Тривиальный бейзлайн (ключевые слова вроде «ignore previous instructions») для нижней планки.

**Готово, когда:** бейзлайн оценён, таблица сохраняется в `results/<детектор>/`.

### Этап 3. Подходы 1 и 4 (дни 3–4) - выполнен

- **Эмбеддинги + классификатор:** многоязычная модель эмбеддингов (например, из семейства multilingual-e5), поверх неё логистическая регрессия, kNN и маленький MLP. Подбор гиперпараметров на val.
- **LLM-судья:** промпт с определением атаки и few-shot примерами из train, ответ в строгом формате (метка + уверенность). Модель: Haiku 5.5. Температура не передаётся (только значение по умолчанию), ответы кэшируются.
- Отдельно проверить, как судья ведёт себя на примерах, которые пытаются обмануть его самого.

**Готово, когда:** оба подхода в таблице сравнения.

### Этап 4. LoRA и prompt tuning (дни 5–6) - выполнен: LoRA работает, prompt tuning дал отрицательный результат

- Базовая модель: небольшая многоязычная энкодерная модель (например, xlm-roberta-base или mdeberta-v3-base), задача: классификация последовательности.
- Ноутбуки для Colab: библиотеки `transformers` + `peft`, обучение на train, ранняя остановка по val.
- Prompt tuning на той же базовой модели, чтобы сравнение было честным.
- Скачать адаптеры, подключить в `detectors/implementations/lora.py` и `prompt_tuning.py`. LoRA подключена: вероятности на val и golden считает Colab и читаются из `results/lora-xlmr/adapter/`, замер задержки на CPU не сделан (базу xlm-roberta локально скачать не удалось).

**Готово, когда:** все 4 одиночных подхода в общей таблице. Prompt tuning в таблице с отрицательным результатом: три запуска и диагностика, подробности в [RESULTS.md](RESULTS.md), раздел 9.

### Этап 5. Каскад (день 7) - выполнен

- Ступень 1: лучший быстрый детектор. Ступень 2: судья.
- Два порога уверенности (ниже: безопасно, выше: атака, между ними: судья).
- Перебор порогов на val, кривая «точность против доли запросов на ступень 2», выбор рабочей точки, финальная оценка на golden.

**Готово, когда:** каскад в таблице, построен график компромисса. Три каскада и график: [RESULTS.md](RESULTS.md), разделы 6 и 8, `results/figures/cascade_tradeoff.png`.

### Этап 6. Шлюз (дни 8–9) - выполнен

- **Шлюз** (`services/backend/gateway/`): `POST /check` принимает тему, тело письма (текст или HTML) и выбранный детектор. Тема и тело проверяются вместе, из HTML извлекаются видимый и скрытый текст. Возвращает метку, уверенность, сработавшую ступень, задержку. При опасном письме отказ: до ассистента клиента оно не доходит. `GET /detectors` показывает готовые детекторы и причины недоступности остальных, `POST /compare` прогоняет письмо через все готовые детекторы по очереди и возвращает вердикт каждого, `GET /metrics` отдаёт агрегаты. Журнал решений в SQLite или JSONL. Вложения и заголовки кроме темы не разбираются, это ограничение записывается в документацию.
- `compose.yaml` поднимает три сервиса (nginx, frontend, backend): `docker compose up`, затем `http://localhost:8080` (образы пересобираются из кэша слоёв).
- Опционально: MCP-обёртка над `/check`.

**Готово, когда:** шлюз возвращает вердикт (атака/нет), уверенность и сработавшую ступень для письма с инъекцией и для обычного письма. Проверка последствий (утечка секрета у реального ассистента) вне объёма проекта: это ответственность клиента, который встраивает шлюз перед своим ассистентом.

### Этап 7. Адаптивные атаки (дни 10–11) - отложен

Изначальная идея: атаковать собственные детекторы так, как это сделал бы взломщик (атакующая модель переписывает письмо, пока детектор не пропустит), проверить обход на мишени с фиктивным секретом и дообучить детектор на найденных обходах. 

**Готово, когда:** решение принято - не входит в объём этой работы.

### Этап 8. Визуализация и демо (день 12) - страница демо готова, графики и видео не сделаны

- `eval/plots.py`: таблица сравнения, кривая каскада, recall по категориям.
- `services/frontend/public/`: страница демо (готова, статика без сборки, светлая тема, оформление в духе shadcn/ui и чат-интерфейсов). Поля «Тема» и «Текст», выпадающий список готовых примеров (обычное письмо, прямая атака, скрытая команда в HTML, цитата атаки в предупреждении), выбор детектора или кнопка «все детекторы» (таблица вердиктов каждого: метка, уверенность, ступень), вердикт и ступень. Панель со счётчиками из `/metrics`.
- Записать видео полного сценария как запасной вариант.

### Этап 9. Выступление и статья (день 13)

- Слайды: проблема → архитектура → подходы → golden set → результаты → каскад → ограничения → выводы.
- Репетиция с таймером.
- Черновик статьи: введение, постановка, методика, эксперименты, результаты, ограничения, выводы.

## Проверка

- `uv run eval/run_eval.py --detector <name>` для каждого подхода выводит метрики на golden.
- `docker compose up`, затем `POST /check` (или страница демо): письмо с инъекцией получает вердикт `attack` и действие `block`, обычное письмо `benign` и `allow`.
- Повторный прогон оценки даёт те же цифры (кэш ответов LLM).
- Golden не пересекается с train и val (проверка по id и по близости эмбеддингов).
